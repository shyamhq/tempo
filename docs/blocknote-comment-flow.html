// apps/console/server/plan.ts (sketch)
export async function getPlanForAgent(threadId) {
  const { plan_doc, plan_md } = await getThread(threadId);
  const threads = await threadStore.getThreads();

  // Walk plan_doc, find every commentThread mark, collect its inline text
  // and the sentence it sits in.
  const anchors = extractAnchors(plan_doc);
  // → [{ threadId: "t_abc", anchor_text: "presigned URL",
  //      context: "Use multipart form upload with a presigned URL." }]

  return {
    markdown: plan_md,
    comments: anchors.map((a) => {
      const t = threads.get(a.threadId);
      return {
        id: a.threadId,
        anchor_text: a.anchor_text,
        context: a.context,
        resolved: t.resolved,
        thread: t.comments.map((c) => ({
          author: c.userId,
          text: bodyToText(c.body),  // flatten BlockNote blocks → string
          at: c.createdAt,
        })),
      };
    }),
  };
}
Why a side-channel and not inline markdown markers? Markdown has no comment syntax. Inlining markers (e.g. {{comment:t_abc}}…{{/comment}}) would force the Agent to write them back exactly — high foot-gun. A side-channel keeps the markdown clean and pushes anchor-matching to the server, where we can be deliberate.
↓   Agent decides: "good point — add the lifetime constraint to the line." Calls tempo_write_plan(thread_id, new_markdown).
Stage 4

Agent writes back. Server reconciles the comment anchor.

Agent ships fresh markdown. Server parses to a new block tree, walks every existing thread mark, and re-anchors by substring-matching anchor_text then context. The comment stays attached to the rewritten line; if the anchor text vanished entirely, the thread is flipped to orphaned.

That callout is the strawman. Substring matching is the simplest reconciler and the most brittle. The next section walks four real options, with a worked example for each on the same Plan + comment.

Reconciliation, four ways

Stage 4 is where strategy matters. The Agent rewrites markdown; the server has to decide what happens to the comment anchor. Four real options, ordered cheapest-and-brittlest to richest-and-safest. The first is what Notion does inside the editor (and what Tempo cannot do over the markdown wire today). The third is what I'd build for Tempo.

Lossless / correct Soft anchor — comment survives with shrunk/expanded range Orphan / wrong-anchor

A

In-place ProseMirror transaction

What Notion's AI does inside the editor. The wire format is a transaction, not new markdown.

The Agent emits a position-scoped transaction against the doc: 

tr.delete(40, 53)           // "presigned URL"
tr.insert(40, "presigned URL (lifetime ≤ 15 min)")

ProseMirror's mark inheritance does the work for free: the insertion sits inside the existing commentThread mark range, so the new text inherits the mark. No reconciliation logic on the server; no offset bookkeeping; no edge cases. The mark survives any edit that happens inside its range.

EasyMediumHard
Lossless

Insertion inside the mark range; mark wraps the longer text automatically.

 Lossless

If the Agent's transaction targets the exact mark range, mark inheritance wraps "signed URL" — same as the in-Notion test you just ran.

 Orphan

The Agent replaces the wider sentence range that contains the mark. The mark falls outside the replacement; ProseMirror drops it. Notion sends this to "All comments" without a visible anchor.
Why Tempo can't use it. Two reasons: (1) the MCP protocol gives the Agent markdown, not ProseMirror positions — an LLM emitting tr.delete(40, 53) against an unseen doc is a foot-gun; (2) every Plan revision would have to fit into a single transaction shape, which doesn't compose with multi-region edits. Markdown wins for the LLM-author surface; Tempo accepts the cost of reconciling afterward.
B

Substring matching (the strawman)

Server searches new markdown for the saved anchor_text; if found, applies the mark. This is what I drew in Stage 4 above.

For each existing thread, the server runs new_md.indexOf(anchor_text). Hit → apply mark there. Miss → fall back to the context substring. Miss again → orphan.

EasyMediumHard
Re-anchored

"presigned URL" still appears verbatim. Wins.

 Orphan

"presigned URL" is gone (now "signed URL"). Fallback to context ("Use multipart form upload with a presigned URL.") also misses. Comment falls off into the orphan list even though the meaning is intact.

 Orphan

No substring match anywhere. Correct outcome — the comment should orphan — but for the wrong reason (luck, not logic).

The two real failure modes beyond what the table shows:

  • Ambiguity. If "presigned URL" appears twice in the new Plan, indexOf finds the wrong one. No way to disambiguate from a string alone.
  • Position drift. If the Agent moved the discussion of presigned URLs to a different section, the mark follows the substring — anchoring on the wrong sentence.
C

Markdown-diff alignment (recommended)

Save the mark's character offset in the old markdown; on rewrite, diff old → new and map each offset through the diff. Same algorithm GitHub uses for PR review comments across force-pushes.

When the mark is placed, store { thread_id, start_offset, end_offset } against the markdown that existed at that moment. On rewrite, run a text diff (Myers or patience — pick a library), then for each mark walk the diff hunks and translate its offsets to the new document.

Worked example on the medium case ("presigned URL" → "signed URL"). The old markdown's relevant line:

EasyMediumHard
Lossless

Diff sees a pure insertion outside the mark; offsets unchanged.

 Soft anchor

Mark range shrinks to surviving text — the comment now anchors "signed URL" and the Console flags it soft-reanchored so the Dev can confirm.

 Orphan (correct)

The entire mark range is inside a deletion hunk → no surviving offsets → thread goes orphaned. The Dev sees it in the sidebar with the original anchor text, "presigned URL", so they know what was being discussed.
Why this is the right choice for Tempo. It gives us Notion-equivalent stickiness without changing the wire format. The Agent keeps writing markdown; the server keeps the position bookkeeping. Failure modes are honest: shrinking is visible (soft flag), orphaning surfaces the original anchor so the Dev can react. No silent wrong-anchoring like Strategy B.
≠

A vs C — they share verdicts, not mechanisms

Both come out lossless on Easy and Medium, but the path is fundamentally different. The cleanest framing is temporal.

A — In-place transaction C — Diff alignment
When the mark moves During the edit, in the same operation After the edit, as a second pass
Where the logic lives ProseMirror's mark-inheritance plugin (already shipped) Custom server code — Myers diff + offset translator
Wire input from the Agent A position-scoped op: tr.delete(40,53); tr.insert(40, …) A full markdown string
Doc state without the mark Never exists — the transaction carries the mark forward atomically Briefly exists, between markdown-parse and offset-reapply — must wrap in a DB tx so no reader sees it
Ambiguity if anchor text repeats Impossible — positions are unique Impossible — saved offset identifies a specific occurrence
Soft-anchor middle state Not a thing — marks are atomic First-class — offset map produces a sub-range, Dev sees a "soft" flag
What you'd need to build Nothing on the server — but Agent has to emit ProseMirror positions Diff library, offset translator, reapply pass — all server-side
The pithy version. A is "the edit and the mark-move are one transaction." C is "the edit happens, marks are gone, then we recompute where they should be." A would be lossless-by-construction if the Agent could speak ProseMirror. C is lossless-by-reconstruction over markdown. Same destination, different vehicles — and C has one feature A can't offer (the soft-anchor middle state).
D

Block-tree wire format

Skip markdown entirely — Agent reads and writes BlockNote JSON, with marks already inline.

The MCP tools change: tempo_get_plan returns the raw plan_doc (block tree + marks) instead of markdown; tempo_write_plan accepts a block tree back. No reconciliation needed — marks travel with their inline runs through the round-trip.

EasyMediumHard
Lossless

Trivially — Agent edits the marked inline run in place.

 Lossless

Agent keeps the mark on the new inline run when rewriting; mark survives.

 Orphan

Agent deletes the marked run as part of a wider replacement. Same fate as Strategy A — the mark has no host.
Why we don't pick this today. LLMs are bad at producing well-formed structured JSON that round-trips through a strict schema. They hallucinate block IDs, malform marks, drop required fields. To make this safe we'd need: (a) a Zod schema for every block type, (b) a server-side validate-and-repair pass, (c) probably a retry loop with the validation errors fed back. Markdown sidesteps all of that — and we still get correct reconciliation via Strategy C. Revisit if/when Tempo grows a typed-tool surface where the Agent edits via targeted operations (e.g. tempo_edit_block(id, newContent)) rather than wholesale-rewriting the Plan.

Reviewing Agent edits — Accept / Deny

Right now Tempo's loop is "Agent rewrites → Plan visibly changes → Dev reads new version." There's no review gate, so a bad rewrite goes live and the Dev's only recourse is to leave a new comment. Thin trust for a product whose pitch is "the Agent edits your Plan." Three patterns to choose from, then the one I'd build and how it threads through the data model.

Σ

Three product patterns

Each one is a real pattern from a real tool. Trade-offs differ in surface area, not in difficulty.

PatternHow it feelsTrade-off
1 — Live + revert
Git-style undo		 Agent edits land immediately. A sidebar lists recent revisions; Dev can revert a paragraph back. Quick to build. Weak review surface — easy to miss bad edits if the Dev wasn't watching.
2 — Pending changes panel
Cursor's "Apply" flow		 Agent's edits collect in a side panel. Dev opens it, sees a list of proposed changes, clicks Apply or Discard per change. Discoverable. But changes are reviewed out-of-context — Dev sees the snippet, not the surrounding Plan.
3 — Inline suggestion mode
Recommended — Google Docs' Suggesting mode		 Agent's edits appear as colored insertions / strike-through deletions in the Plan itself. Per-change hover affordances: ✓ Accept, ✗ Reject. Top-of-Plan banner with Accept-all / Reject-all. Highest implementation cost (custom marks + UI affordances), highest review fidelity. Composes with comments — the Dev can leave a comment on a proposed change before accepting it.
Why Option 3. Tempo's editor is the Dev's primary surface. Pattern 3 keeps review in the same view where the Plan is being read — the Dev evaluates a change against its context, not against a panel snippet. It also gives comments a natural relationship to proposed edits ("here's why I'm rejecting"). Patterns 1 and 2 are easier to ship but trade away Tempo's core promise.
✓

Data model for inline suggestions

A new mark type, two endpoints, one SSE event. The canonical Plan never changes until the Dev decides.

BlockNote supports custom marks. We add a suggestion mark with shape: 

{
  "type": "suggestion",
  "attrs": {
    "op": "insert" | "delete",
    "changeId": "ch_xyz",
    "author": "agent",
    "proposedAt": "2026-06-06T16:42:00Z"
  }
}

When the Agent calls tempo_write_plan(threadId, new_md), the server doesn't replace plan_doc. It runs a diff old_md → new_md, walks the hunks, and encodes them into the existing plan_doc as suggestion marks:

  • Each insertion hunk → new inline run added at the old position, wrapped in suggestion-insert.
  • Each deletion hunk → the existing inline run is wrapped in suggestion-delete (not removed yet).
  • Each replacement hunk → one delete + one insert at the same position.

Result: a single plan_doc where both the original prose and the Agent's proposed prose co-exist, marked. Server fires SSE plan_changes_proposed with the list of changeIds.

Accept / reject flow + comment interaction

Two endpoints. The comment-reconciler from Part 2 (Strategy C) only runs on accepted ops.

Accept POST /api/threads/:id/plan/changes/:changeId/accept → server reads the suggestion mark and:

  • suggestion-insert → strip the mark, keep the wrapped text.
  • suggestion-delete → strip the mark and remove the wrapped text.

Reject POST /api/threads/:id/plan/changes/:changeId/reject → server reads the suggestion mark and:

  • suggestion-insert → strip the mark and remove the wrapped text.
  • suggestion-delete → strip the mark, keep the wrapped text.

After an accept, the comment reconciler (Strategy C) runs against just the accepted op. The diff is small — usually a single inline range — so offset translation is cheap. The comment either rides along, soft-anchors, or orphans, as in Part 2.

Comment-on-change. Because suggestions are encoded as marks in the Plan, a Dev can highlight a proposed insertion and leave a normal comment on it — anchored to the suggestion mark range. The reply chain becomes the discussion of "should we accept this change?" Reject → suggestion mark is gone and the comment auto-orphans (correctly — the thing being discussed was withdrawn). Accept → the suggestion mark is stripped but the comment mark stays, anchored to what's now canonical text. Same Strategy C reconciliation handles both.

The Agent doesn't change. It keeps reading and writing markdown. The "proposals don't auto-apply" semantic is enforced entirely on the Console side. The Agent doesn't even know its writes are pending until the next tempo_get_plan reads canonical-only state.
Storage shape, when this leaves the playground: two columns on the existing threads row — plan_doc (BlockNote block-tree JSON, replaces today's Tiptap JSON) and plan_md (cached derived markdown). The threadStore is a new pair of tables — plan_threads(thread_id, plan_id, resolved, metadata) and plan_thread_comments(comment_id, thread_id, user_id, body_blocks, created_at) — with a small ThreadStore implementation that reads/writes those tables (this is what BlockNote calls a "custom ThreadStore" — they ship YjsThreadStore, TiptapThreadStore, RESTYjsThreadStore; we'd add TempoThreadStore). Comments and replies do not need a Yjs document at rest — only the playground uses Yjs because it's the path of least resistance for an in-memory single-user demo.
