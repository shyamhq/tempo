Plan ↔ Agent data flow

How the Plan moves between BlockNote (Console) and the local Claude Code Agent over MCP. Storage is BlockNote's JSON blocks tree; the wire format the Agent sees is annotated Markdown with sentinel tags. A sidecar map kept server-side carries the inline styling and comment metadata that Markdown cannot express, and gets re-attached when the Agent's response is decoded back into blocks.

Scenario throughout: the Plan contains the sentence “Anchoring on rock-solid block IDs becomes the default”. The Dev coloured rock-solid pink and added a comment on the same range. The Agent will rewrite the surrounding sentence but leave the styled phrase intact.

Stage 3

MCP server — encode blocks → annotated markdown + sidecar

apps/console/server/plan/encode.ts

When the Agent asks for the Plan, the server walks the blocks tree and emits Markdown. Anything Markdown can't express (custom styles, comment marks, block-id stability we want to preserve) becomes an inline sentinel tag with a short id. A sidecar map keyed by those ids stays server-side and never leaves the process.

Encoder pseudocode
function encodeForAgent(blocks): { markdown: string; sidecar: Map } {
  const sidecar = new Map();
  const mintId = shortIdFactory();        // 4-char base32

  for (const block of blocks) {
    sidecar.set(`b-${block.id}`, { kind: 'block', id: block.id, props: block.props, type: block.type });
    // Walk inline content, wrapping runs whose styles include anything non-markdown.
    for (const run of block.content) {
      if (hasNonMarkdownStyles(run.styles)) {
        const id = mintId();
        sidecar.set(id, { kind: 'inline', styles: run.styles });
        emit(`<x-mark id="${id}">${run.text}</x-mark>`);
      } else {
        emit(run.text);                  // bold/italic/code → vanilla markdown
      }
    }
  }
  return { markdown: assembled, sidecar };
}
Sentinel choice. <x-mark id="…"> is pseudo-XML — the model recognises it as structured markup and tends not to "tidy" it. The parser is tolerant: an unmatched tag drops its styling but never breaks the write.

The Plan you read may contain markers of the form
  <x-mark id="XXX">…</x-mark>
These mark inline ranges the Dev has styled or commented on.
Rules:
  1. Keep every <x-mark> paired. Open and close must match by id.
  2. The marker wraps whatever text the styled range currently
     contains. If you edit the text inside, the styling follows
     the new wording — that is intentional.
  3. Do not invent new ids. Do not split a single id across the
     document.
  4. You may move a marker's text inside the same block. Crossing
     block boundaries: keep each block's portion as its own pair
     with the same id (the server rejoins them by id).
  5. If you delete the styled range entirely, drop both tags.

Everything outside markers is ordinary chat-style markdown.

Stage 6

MCP server — decode markdown + sidecar → blocks

apps/console/server/plan/decode.ts

The server pulls every <x-mark> pair out of the incoming Markdown, records the text range each one covered, strips the tags, runs the clean Markdown through tryParseMarkdownToBlocks, then walks the resulting blocks and re-attaches styles from the sidecar at the recorded offsets.

Decoder pseudocode
function decodeFromAgent(markdown, sidecar): Block[] {
  const ranges = [];                      // { id, start, end }
  const clean = stripSentinels(markdown, ranges);

  const blocks = await serverEditor.tryParseMarkdownToBlocks(clean);

  for (const { id, start, end } of ranges) {
    const entry = sidecar.get(id);
    if (!entry) continue;                // agent fabricated an id — ignore
    splitAndAttachStyles(blocks, start, end, entry.styles);
  }

  reconcileBlockIds(blocks, sidecar);          // keep stable IDs where text matches
  return blocks;
}
Graceful degradation. Unmatched open / close tags log a warning and lose just that range's styling. The Plan is never corrupted by a bad model response — at worst, one inline style drops and the comment re-anchors via the quote+context fallback.

Edge cases

How the protocol behaves under stress

Reference
A. Multi-block range (comment spans three paragraphs)

Encoder splits the range into one matched pair per block, sharing the same id. Decoder rejoins them by id into one logical anchor. The Agent's job stays block-local.

Block A: …end of paragraph one <x-mark id="k9w">last sentence here.</x-mark>

Block B: <x-mark id="k9w">An entire middle paragraph the comment covers.</x-mark>

Block C: <x-mark id="k9w">The first sentence of three</x-mark> and then the rest of C…
B. Agent deletes the styled phrase entirely

The Agent drops both tags. Sidecar entry is orphaned; decoder ignores it; the comment falls into the quote+context fallback (and likely surfaces as "Unanchored" in the UI).

C. Agent inserts new text outside any marker

No sentinel was minted for the new range. It comes back as a fresh inline run with empty styles. Expected behaviour — new Agent text is unstyled.

D. Agent fabricates a marker id

Sidecar lookup misses. Decoder logs a warning and drops the marker; the wrapped text becomes ordinary content. No data loss, only styling loss on that fabricated range.

E. Unmatched open or close tag

Tolerant parser: unmatched halves are dropped silently with a warning. The Plan write still succeeds. Telemetry counts these so we can see model discipline over time.

F. Block-level customs (ConfluenceCodeBlock with mermaid)

Encoded as a fenced code block in Markdown — the Agent already understands fences and leaves them alone. No sentinel needed.

Summary

Who owns what

Boundaries
Console

Reads and writes blocks JSON. Never sees Markdown. Never sees sentinels. Comments are BlockNote-native inline marks; no anchor math in client code.

MCP server

Single source of truth for the encoder, decoder, and the sidecar map (per-request). Both tempo_pull_plan and tempo_write_plan exist in the same process; the sidecar lives in memory between them, keyed by the request that owns it.

Claude (Agent)

Reads Markdown with inline <x-mark> markers. Writes Markdown back, preserving paired markers. Mental model unchanged from today.

Storage

One column: plans.body_blocks (JSON text). The old body_markdown column is dropped in the same migration.
