Comment persistence — Options A, B, C

The bug: Dev creates a comment, refreshes, comment disappears. The root cause: BlockNote's CommentMark is tagged blocknoteIgnore: true, so it never lands in the blocks-JSON we persist. Three ways to fix it, with the trade-offs that matter.

survives the anchor still finds its text and renders flaky works most of the time but can mis-anchor orphans the row stays in the DB but the comment doesn't render

A Quote + context re-anchor

Store the selected text and a ±60-char window of surrounding text alongside each Comment. On every editor mount, walk through the comments and re-stamp the BlockNote mark by finding the quote in the document.

Data model

comments
  id            cmt_…
  thread_id     thr_…
  plan_quote    "the auth service"   ← filled in
  plan_context  "We will rewrite the auth service before"   ← filled in
  replies[]     …

How the round-trip works

Create
Dev selects the auth service and writes a comment. Composer reads ProseMirror selection → captures the quote + a ±60-char window of context → sends to POST /api/threads/:id/comments. BlockNote stamps the in-memory mark; auto-save persists the blocks JSON (mark is stripped — that's fine, we don't rely on it).
Refresh
Editor mounts with the saved blocks JSON. A useEffect walks view.comments, and for each one searches the editor's text for plan_quote. If the quote appears once, it uses that. If it appears multiple times, it picks the occurrence whose surroundings best match plan_context. Then it stamps the mark via TipTap.

Scenarios

1. Refresh, no other edits survives

Document unchanged. Quote found exactly once. Mark stamped. Same UX as the original Tempo build.

2. Dev edits an unrelated paragraph and refreshes survives

The quote text is untouched, so it's still found in the doc. Surroundings don't matter — we don't need the context to be intact.

3. Agent rewrites the surrounding sentence but keeps the quoted text survives
BEFORE  We will rewrite the auth service before shipping v2.
AFTER   We're planning to upgrade the auth service in Q3.

Quote is still the auth service. Found. Anchored.

4. The quote appears twice; context disambiguates survives
The the auth service needs rewriting before v2.
Database migration depends on the auth service being stable.

Both occurrences. Context window says "rewriting before v2" — the first occurrence wins.

5. The quote appears twice; surroundings change a lot flaky

Both surrounding contexts changed past the 60-char window's tolerance. The match falls back to the first occurrence found, which may or may not be the one the Dev meant. Mis-anchor is possible but rare in practice.

6. Agent rewrites the quote itself orphans
BEFORE  We will rewrite the auth service before shipping v2.
AFTER   We will rewrite the auth service the authentication module before shipping v2.

Quote string isn't in the document anymore. Comment becomes orphan — row stays in the DB but isn't shown anywhere on the page.

verdict
Smallest change to fix the reported bug. Covers refresh + most editing scenarios. Loses comments only when the quoted text itself is rewritten — accepted trade-off in the original migration plan.

B Store ProseMirror JSON instead of blocks JSON

Change what we persist. Instead of editor.document (blocks JSON, which strips marks), save editor._tiptapEditor.getJSON() (full ProseMirror state, marks intact). BlockNote's native round-trip carries the comment mark across save / load cycles.

Data model

plans
  thread_id     thr_…
  body_pm_json  { "type":"doc", "content":[ ... marks: [{ type:"comment", attrs:{ threadId:"cmt_…" } }] ] }
  updated_at    …

How the round-trip works

Create
Dev creates comment. BlockNote stamps mark on PM state. Auto-save writes the PM JSON (which includes the mark) to the DB.
Refresh
Editor loads PM JSON via editor._tiptapEditor.commands.setContent(pmJson, false). Marks are restored verbatim — no re-anchoring needed. BlockNote sees the marks, asks the bridge for each thread's data, renders comments inline.
Agent reads
Server converts PM JSON → blocks → annotated Markdown (via ServerBlockNoteEditor._prosemirrorJSONToBlocks). Marks are dropped during the blocks step — agent sees clean Markdown.
Agent writes
Markdown → blocks → PM. The new PM has no comment marks (they were stripped on the way out and never came back). We still need a re-anchor step here — same algorithm as Option A — to migrate the old marks onto the new PM tree by finding their quotes.

Scenarios

1. Refresh, no other edits survives

Marks restored verbatim from PM JSON. No searching, no risk of mis-anchor.

2. Dev edits anything (same session, before refresh) survives

PM state preserves mark positions across edits — text added before a marked region shifts the mark's PM position automatically (this is what TipTap and ProseMirror are designed to do). Saves capture the current PM positions. Loads restore them. Marks always land on the same text.

3. Agent rewrites surrounding text survives

Same as Option A — the re-anchor algorithm finds the quote in the new PM tree and stamps the mark.

4. Agent rewrites the quoted text itself orphans

Same accepted limit as Option A. Storing PM JSON doesn't help here because the agent never sees the marks — it can't preserve them.

Cost of the switch

  • New DB column or repurpose body_blocks as body_pm_json. One migration.
  • Agent encoder changes: getPlanForAgent goes PM → blocks → Markdown instead of blocks → Markdown.
  • Agent decoder changes: writePlanFromAgent goes Markdown → blocks → PM instead of Markdown → blocks, plus the re-anchor step.
  • PM JSON is bigger on the wire than blocks JSON (≈1.5–2×).
  • We become coupled to editor._tiptapEditor internals (a private-ish escape hatch in BlockNote).
verdict
Biggest behavioural win for Dev-only round-trips (zero re-anchor risk, no flaky cases). Doesn't help the agent path — that still needs A's algorithm. Bigger change, more coupling to TipTap.

C Both — PM JSON for storage and quote/context re-anchor for the agent path

Belt and braces. Store PM JSON so Dev round-trips are lossless. Also save plan_quote + plan_context per comment so the agent rewrite path has a re-anchor fallback. This is the "everything works" version.

Where each piece carries its weight

ScenarioA onlyB onlyC (both)
Refresh, no other edits ok ok ok
Dev edits unrelated text + refresh ok ok ok
Dev edits text near the comment ok (if quote intact) ok (PM tracks positions) ok
Quote appears twice, ambiguous flaky ok (mark is positional) ok
Agent rewrites surrounding text ok ok (via A's algorithm) ok
Agent rewrites the quoted text itself orphan orphan orphan

Cost

  • Everything in B (storage change, encoder/decoder seam, TipTap coupling).
  • Plus the capture-quote-and-context plumbing from A (composer reads selection, bridge forwards metadata).
  • Plus the re-anchor algorithm (used only on the agent-write path now, since Dev round-trip is covered by PM storage).
verdict
Strictly the most robust option. Strictly the most code. Pays off if you expect heavy concurrent Dev + Agent editing of the same regions; overkill if Devs mostly comment on stable text and the Agent mostly edits other sections.

The "agent rewrites the quoted text itself" row is the same across all three options because comments fundamentally anchor to specific text. The only way to survive a quote rewrite is to teach the agent that the text is anchored (e.g. via the ⟦sty:…⟧ sentinel pattern from the original Plan encode/decode flow) — that lives in a different layer and is orthogonal to A / B / C.
