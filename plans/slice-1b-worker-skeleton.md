# Slice 1b — `apps/worker` skeleton with stub `tempo_attach`

## Problem statement

`plans/agent-harness.md` commits Tempo to a topology flip: the user's own
Claude Code binary connects to a remote MCP endpoint Tempo hosts, and a
second runtime (Hosted) runs the Claude Agent SDK loop inside an
ephemeral VM driven by Worker. Both runtimes call the same `tempo_*` MCP
surface, hosted by a new app `apps/worker` that owns the unified MCP
endpoint, the connector Gateway, the Mailbox, and the Hosted SDK driver.

Slice 1a (committed) extracted `packages/db` so Console and a future
Worker can share the Drizzle schema + client. Slice 1c will migrate the
17 MCP-adjacent routes from Console to Worker and reshape `apps/agent`
into a thin `tempo-agent init` CLI. **Slice 1b is the bridge between
them:** it stands up `apps/worker` as a deployable app with an Express
+ `@modelcontextprotocol/sdk` v1.29+ HTTP-streamable MCP endpoint,
authenticated by the existing workspace API key (Bearer), serving
exactly **one** stub tool — `tempo_attach` — that reads via `@tempo/db`
and returns the same shape Console currently returns from
`GET /api/sessions/:id/state`.

After 1b lands, the user can configure their Claude Code's `.mcp.json`
manually to point at Worker, call `tempo_attach`, and receive a real
response. Console's existing CLI flow keeps working unchanged. No
routes move, no browser code changes, no embedded SDK loop deleted.

## Smallest concrete change

**New app.** `apps/worker/` with:

```
apps/worker/
├── package.json           bun/node, deps: express, @modelcontextprotocol/sdk,
│                          @tempo/db, @tempo/contracts, pino, zod. Dev deps:
│                          typescript, @types/{express,node}. Scripts:
│                          dev (bun --watch run src/index.ts), build, start,
│                          typecheck, lint.
├── tsconfig.json          extends ../../tsconfig.base.json
├── Dockerfile             multi-stage bun→node:20-slim, mirrors apps/console
├── fly.toml               new Fly app `tempo-worker`, healthcheck on /health,
│                          proxy_buffering off for streaming MCP
└── src/
    ├── index.ts           Express boot: mounts /health and /mcp routes,
    │                      logger init, env validation, graceful shutdown.
    ├── env.ts             Zod-validated env: DATABASE_URL, PORT,
    │                      WORKER_LOG_LEVEL, NODE_ENV.
    ├── logger.ts          Pino instance — stdout in dev (pretty), JSON in prod.
    ├── auth.ts            Bearer middleware: extracts `sk_agent_*` from
    │                      Authorization header, looks up workspace in
    │                      `@tempo/db`, attaches `{ workspaceId, memberId }` to
    │                      req.locals. 401 on any failure.
    ├── mcp/
    │   ├── server.ts      registers MCP server (`name: "tempo"`, `version: "0.2.0"`)
    │   │                  with one tool: `tempo_attach`.
    │   ├── transport.ts   StreamableHTTPServerTransport lifecycle —
    │   │                  per-Mcp-Session-Id store, init/resume/close flow.
    │   └── tools/
    │       └── attach.ts  reads `tempo_attach` data via `@tempo/db`, returns
    │                      the same shape Console's GET /api/sessions/:id/state
    │                      does today (Plan + open Comments + recent Discussion
    │                      Messages + workflow guide + latest_event_id).
    └── routes/
        └── health.ts      GET /health — JSON 200 with version + db-ping result.
```

**Root tweaks.**

- `package.json`: add `dev:worker`, `build:worker`, etc. scripts.
- `turbo.json`: declare `@tempo/worker` build/dev/typecheck/lint tasks
  with the same shape as `@tempo/console`.
- `Dockerfile`: untouched (Console's Dockerfile only builds Console).
  Worker has its own Dockerfile.
- `bun.lock`: regenerated by `bun install`.

**No code moves.** All 17 Console routes stay in Console. No Console
files are edited.

**Tool surface.** Exactly one tool. `tempo_attach` reads:

- Thread row (title, description, status)
- Plan blocks via `apps/console/server/plan.ts` query logic (re-implemented
  in `apps/worker/src/mcp/tools/attach.ts` using `@tempo/db` directly —
  not by importing from Console, which would back-couple the apps).
- Open Comments + recent Discussion Messages + workflow guide constant +
  `latest_event_id` from the events table.

The same Zod output schema `@tempo/contracts/mcp` `AttachOutput`. Wire
contract unchanged.

**Skills bundle.** Out of scope for 1b. `tempo_load_skill` lives in
Console-served MCP today (via the CLI's embedded server). 1b doesn't
serve skills; the stub `tempo_attach` returns the workflow guide
inline. Skills move in 1c when the rest of the MCP surface migrates.

**Local Agent config.** The user's Claude Code does NOT auto-discover
Worker in 1b. For smoke-testing, the Dev manually adds an MCP entry to
their `.mcp.json`:

```json
{
  "mcpServers": {
    "tempo-remote": {
      "type": "http",
      "url": "https://tempo-worker.fly.dev/mcp",
      "headers": { "Authorization": "Bearer ${TEMPO_API_KEY}" }
    }
  }
}
```

`tempo-agent init` writes this file in 1c.

## Alternatives considered

### HTTP framework for Worker

| Option | Tradeoff | Decision |
|---|---|---|
| **Express** | Mature; `StreamableHTTPServerTransport` plugs into `IncomingMessage`/`ServerResponse` directly; zero adapter friction. | **Chosen.** |
| Hono | Edge-first; Node adapter introduces friction for stateful `Mcp-Session-Id` flows per research (agent #1). | Rejected. |
| Fastify | High perf, strong types, but MCP SDK integration untested as of 2026-Q1. | Deferred — revisit if Express bottlenecks. |
| Plain Node `http` | Zero deps; hand-roll auth/logging/CORS. | Rejected — violates "use libraries to avoid hand-wiring." |

### MCP transport

| Option | Tradeoff | Decision |
|---|---|---|
| **`StreamableHTTPServerTransport`** (v1.29+) | Spec-current; supports session resumption via `Mcp-Session-Id`; the only production option per research. | **Chosen.** |
| SSE transport | Deprecated in spec. | Rejected. |
| `StdioServerTransport` | Today's CLI shape; doesn't work over the network. | Rejected — the entire point of 1b is remote MCP. |

### Session-state location

| Option | Tradeoff | Decision |
|---|---|---|
| **In-memory `Map<sessionId, transport>`** | Simple; correct for a single Worker instance. | **Chosen for 1b.** |
| Redis-backed | Needed when Worker scales horizontally (sticky sessions or external store). | Deferred — slice 2+ if scaling demands. |

### Auth middleware shape

| Option | Tradeoff | Decision |
|---|---|---|
| **Bearer `sk_agent_*` + DB lookup of workspace** | Matches the existing CLI's auth path; no new auth contract. | **Chosen.** |
| New per-session token issued by Worker | Adds a session-establishment endpoint and a second token type. | Rejected for 1b — the workspace API key is enough; per-Member identity is per-call (slice 1c+ topic). |

### What `tempo_attach` returns

| Option | Tradeoff | Decision |
|---|---|---|
| **Same shape as Console's `GET /api/sessions/:id/state`** | Wire compat with the existing `AttachOutput` Zod schema; CLI works unchanged after slice 1c. | **Chosen.** |
| A reduced "skeleton" payload | Would require a contract bump and a Local Agent code change. | Rejected — contract is frozen. |

### Hosting / deployment

| Option | Tradeoff | Decision |
|---|---|---|
| **New Fly app `tempo-worker.fly.dev`** | Matches `plans/agent-harness.md` §6 mention of Fly; same provider as Console; same Postgres on Railway via DATABASE_URL. | **Chosen.** |
| Same Fly app as Console (two processes) | Tighter coupling between Console and Worker; against the "Worker never runs Agent-generated code" boundary (security). | Rejected. |
| Railway service | Mixed precedent — Console is on Railway per recent memory. | Deferred decision; if the Dev prefers Railway for Worker too, the fly.toml is the only file to drop and a railway.toml replaces it. The app structure is provider-agnostic. |

## Layer assignment

- `apps/worker/src/index.ts` — **app boot** layer (entrypoint). Boots
  Express, wires routes, registers shutdown hooks. No business logic.
- `apps/worker/src/env.ts` — **infra** layer. Env validation only.
- `apps/worker/src/logger.ts` — **infra** layer. Pino setup only.
- `apps/worker/src/auth.ts` — **server middleware** layer. Reads DB via
  `@tempo/db`. Pure auth logic; no business rules.
- `apps/worker/src/routes/health.ts` — **route handler**. Thin: ping DB,
  return JSON.
- `apps/worker/src/mcp/server.ts` — **MCP registry**. Creates the
  `McpServer` instance, registers tools. No business logic of its own.
- `apps/worker/src/mcp/transport.ts` — **MCP transport adapter**. Owns
  the `Mcp-Session-Id` ↔ transport map. Pure protocol plumbing.
- `apps/worker/src/mcp/tools/attach.ts` — **MCP tool handler**. Reads
  via `@tempo/db`. This is the only file with business logic in 1b.
  Mirrors the layer placement we'd give a `server/<domain>.ts` module
  in Console.

This matches CLAUDE.md rule 19 (layer placement): DB / query logic in
the tool handler (which is the Worker equivalent of `server/db-queries/`);
auth middleware separate; transport plumbing isolated; route handlers
thin.

## Deletion test (per CONTEXT.md §3 + judge P5)

- `index.ts` — entrypoint. Required to boot. Keeps.
- `env.ts` — if deleted, env access scatters across files; Zod
  validation also scatters. Concentrates → keeps.
- `logger.ts` — if deleted, Pino config scatters. Concentrates → keeps.
- `auth.ts` — if deleted, every MCP tool handler re-implements Bearer
  parsing + DB lookup. Concentrates → keeps.
- `routes/health.ts` — could inline into `index.ts` (3 lines). Borderline.
  **Decision: keep as separate file** because Fly checks reference it
  by URL; the file is its own seam.
- `mcp/server.ts` — if deleted, tool registration scatters into
  transport plumbing. Concentrates → keeps.
- `mcp/transport.ts` — if deleted, the session map and `Mcp-Session-Id`
  flow would live inline in the request handler. Concentrates → keeps.
- `mcp/tools/attach.ts` — if deleted, the attach handler lives in
  `mcp/server.ts`. Borderline. **Decision: keep separate** because
  slice 1c will add 9 more tools and each will be its own file —
  starting with the pattern now avoids a refactor at the 2nd tool.

No factories, no DI, no `interface I…` / `class …Impl` invented for a
hypothetical second adapter. Only the existing real seams:

- `@tempo/contracts` — Zod schemas; Worker is a new adapter on the same
  seam Console is already on. **Real seam** (now 2 adapters).
- `@tempo/db` — Drizzle schema/client; Worker is a new adapter. **Real
  seam** (now 2 adapters).

## Uncertainties

1. **Fly proxy buffering for streaming MCP.** Research flagged that some
   reverse proxies buffer streaming responses and break HTTP-streamable
   MCP. Fly's default behavior isn't documented for this case; I'll
   set `proxy_buffering off` (or the equivalent fly.toml setting) and
   verify with a manual smoke test. If Fly doesn't expose the knob, we
   may need a `services.protocol = "tcp"` config or a different host.
2. **Bun runtime + Express + MCP SDK.** Research assumed Node. Bun is
   the dev runtime per CLAUDE.md, with Node 20 in production. I'll run
   `bun --watch run src/index.ts` in dev and `node dist/index.js` in
   prod (after bun build) to confirm both work. If Bun has incompat
   with the MCP SDK's Node-stream usage, we run Node in dev too.
3. **Workspace-key lookup query latency.** Auth middleware does a DB
   round-trip on every MCP call. Currently the same cost the Console
   pays. If hot-path latency becomes a complaint, we add an in-process
   LRU cache (slice 2+).
4. **Local Agent `.mcp.json` schema** — Claude Code's MCP config
   format for remote/HTTP servers may have evolved. I'll verify against
   the current Claude Code docs in slice 1c when we ship `init`.

## Destructive actions

**None in slice 1b's implementation.** The slice adds files; deletes
nothing. The new Fly app `tempo-worker` is created via `fly apps
create tempo-worker` on the Dev's terminal — not by the agent. The
Dockerfile and fly.toml are committed but `fly deploy` is the Dev's
call.
