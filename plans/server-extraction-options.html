Server-Domain Extraction · Options

Worker owns agent-touched data. Console is UI + Workspace admin. Today, seven server modules live in both. Four ways to fix it — judged by the deletion test and the leverage they earn.

Business shape (binding)

The Plan is the deliverable. Everything else is scaffolding.

Agent

One LLM identity. Two runtimes: Local (Member's claude over remote MCP) and Hosted (Agent SDK in a per-session VM driven by Worker). Same tempo_* contract.

Worker

Owns every agent-touched table. Hosts the MCP endpoint. Runs the Gateway (allowlist · approve-gate · grant resolution · execution · audit). Drives the Hosted Agent.

Console

UI + Workspace admin only. Renders the Plan, accepts Dev edits, hosts the Discussion panel. No LLM lives here. No agent-data writes.

How candidates are judged

Vocabulary borrowed from improve-codebase-architecture/LANGUAGE.md. Each option is graded on these.

Module
Anything with an interface and an implementation — a package counts.
Interface
Everything a caller must know: types, invariants, errors, ordering.
Depth
Behaviour-per-interface-byte. Deep = small interface, big payoff.
Seam
Where an interface lives — a place behaviour can swap without in-place edits.
Leverage
What callers get from depth.
Locality
What maintainers get from depth — change, bugs, knowledge in one place.
Deletion test
If you delete the module, does complexity vanish (it was a pass-through) or reappear concentrated across callers (it earned its keep)?

Option A · Single shared package Viable

Extract every duplicated module into @tempo/server. Both apps import from it directly. Console keeps its DB connection and SSR reads; Worker keeps the MCP write paths.

Module · Interface · Depth

Module@tempo/server — Tempo's server-domain operations on Postgres+R2.
Interface~30 named exports (one per domain verb: writePlan, appendComment, getThread, …) + a few types.
DepthMedium — interface tracks the schema's verb count.
SeamPackage boundary. In-process; no network.

Deletion test

Delete @tempo/server → complexity reappears as duplicate trees in both apps (exactly today's state). Passes. Concentrates, doesn't move.

Locality · Leverage

  • Locality — a schema change is one file edit.
  • Leverage — Console, Worker, and the upcoming Hosted-Agent driver all import the same surface.
  • Console keeps direct DB access. That contradicts the strict reading of "Worker owns all agent-touched data" — Console can still write events if a route bypasses Worker.
Verdict Cheapest win. Kills the drift. But it doesn't reshape the model — Console retains the ability to write agent-touched rows, even if no current route does. The seam stops drift, not access.

Option B · Worker absorbs everything Recommended shape

Worker is the only home of agent-touched data. Console has no DB code for Plans, Comments, Discussion, Sessions, Threads. Console's SSR pages and surviving routes fetch Worker over HTTP using Clerk JWTs.

Module · Interface · Depth

ModuleWorker — the privileged backend.
InterfaceTwo surfaces only: the tempo_* MCP contract (for Agents) and the browser HTTP routes (for Console). Both already exist; both already live in packages/contracts.
DepthMaximum. Tiny interface, enormous behaviour.
SeamProcess boundary — already there. We stop pretending the seam is anywhere else.

Deletion test

Delete Worker → everything disappears. It is the backend. Passes maximally. The seam is real, two adapters exist (MCP + browser HTTP), invariants concentrate.

Locality · Leverage

  • Locality — one home. A new event kind, a new block type, a new connector all land in one process.
  • Leverage — Console SSR, Hosted-Agent driver, future Slack app, future CLI all read the same backend through the same wire.
  • Honours the business model literally. "Worker owns all agent-touched data" becomes a structural invariant, not a discipline note.

Costs

  • SSR adds one HTTP hop per page render (~10ms in same Fly region). Acceptable for an editor dashboard; cacheable.
  • Console SSR availability depends on Worker uptime. Mitigated by co-location and Worker's existing health checks.
  • ~2–3 new Worker browser routes needed to cover Console's existing reads (GET /browser/threads?space_id=, approve, reopen).
  • Console SSR pages need a Clerk JWT helper to authenticate to Worker. Standard Clerk pattern, no new primitive.
Verdict Strongest alignment with the business model. The duplication doesn't get a shared seam — it disappears, because Console no longer needs the code at all. Hosted-Agent SDK driver lands naturally inside Worker with zero ceremony.

Option C · Vertical domain packages Premature

One package per CONTEXT.md noun: @tempo/plan, @tempo/comments, @tempo/discussion, @tempo/threads, @tempo/events, @tempo/attachments, @tempo/ids. Apps compose what they need.

Module · Interface · Depth

ModulesSeven small packages, each tracking one noun.
InterfacesEach one is small per package, but the total surface across seven packages equals Option A's single surface.
DepthShallow per package — most packages would be 100–200 lines behind a similarly-sized interface.

Deletion test (on the split itself)

Collapse all seven into @tempo/server → nothing reappears. Imports rename, the DAG inside is the same, no behaviour moves. Fails. The split is a pass-through.

Why we'd reject it today

  • "One adapter is hypothetical." There is exactly one consumer pattern per domain (Console SSR + Worker MCP write); a per-noun seam earns nothing.
  • Build cost: 7 × package.json, tsconfig.json, Biome config. Real ceremony, no leverage.
  • Cross-domain edges (comments → events + attachments, plan → events) just become workspace dep declarations — same DAG, more paperwork.
Verdict Premature seams. Revisit only if a second-consumer story appears for one of the nouns (e.g. a standalone Plan renderer service) — at which point that one noun graduates.

Option D · Option B + a typed client package Strong companion

Same data home as Option B (Worker owns everything). Plus a small @tempo/worker-client package — the typed surface Console and any other consumer uses to call Worker. Contracts come from @tempo/contracts; the client is the seam.

Proposed layout

packages/worker-client/      ~150 lines, hand-written
└── src/
    ├── client.ts                createWorkerClient({ baseUrl, getToken })
    └── index.ts

apps/console/
├── hooks/use-worker-api.ts      thin wrapper around createWorkerClient
└── lib/api-client.ts            workerApi() factory — deleted

apps/worker/                  unchanged from Option B

Module · Interface · Depth

Module@tempo/worker-client — the typed handle to Worker.
InterfaceOne factory + N methods, signatures derived from @tempo/contracts. The interface is the wire contract.
DepthMedium — small implementation, but the interface is the test surface for every consumer.
SeamThe client itself. Two consumers exist immediately (Console SSR + Console browser); Hosted-Agent driver and any future app are #3, #4.

Hono hc() vs hand-written

Worker uses Hono in some routes (per Bun + workspace conventions), but mixing handler-typed RPC with our current Zod-validated route style would couple the client to internal route shapes. Hand-written keeps the client locked to the contract, not the handler. ~150 lines, no codegen.

Deletion test

Delete @tempo/worker-client → every consumer rebuilds the same fetch + Zod-parse + token logic. Two consumers (Console SSR + Console browser) already prove it. Passes.

Verdict Pairs with B. Without B, this is just a thin facade. With B, it earns its keep because Console SSR, Console browser, the Hosted-Agent driver, and any future consumer all reach Worker the same way.

Recommendation

Pick the option that makes the business model a structural invariant, not a discipline rule.

Option B, with Option D as a follow-on once a second non-Console consumer arrives (the Hosted-Agent driver). Reasoning, in order:

  • The business shape already chose for us. Worker owns agent-touched data. Option A leaves Console with the ability to write that data; Option B removes it. The architecture should match the policy.
  • The seam already exists. Worker is a separate process with a Zod-validated HTTP surface and an MCP surface. Option B doesn't create a new seam — it stops pretending one isn't there.
  • Hosted Agent ships next. Slice 2 puts an Agent SDK loop inside Worker. In Option B, that driver has zero ceremony (local function calls). In Option A, it would import the shared package and pretend to be in Console's situation.
  • Option C fails the deletion test on the split itself. Premature seams, no leverage, ceremony cost. Park it.
  • Option D is right but not first. Build the client when the second consumer (Hosted-Agent driver) lands and proves the seam. Until then, Console's existing useWorkerApi + workerApi() factory is already half of D — promoting it to a package is a half-day move whenever you want.

Fallback: if SSR latency turns out to be unacceptable in measured load tests for a specific page (the Plan editor's first paint), pull that page's reads into a thin shared module under packages/server. Hybrid is cheap; don't pre-empt it.

Migration sketch · Option B

Five small commits, no destructive moves until the new path is proven.

  1. Add Worker browser routes that don't yet exist — GET /browser/threads?space_id=, POST /browser/threads/:id/approve, POST /browser/threads/:id/reopen. Console keeps its old paths for now.
  2. Rewire Console SSR + surviving routes to fetch Worker — page by page. Old DB-reading code stays parallel; new fetch path lives behind a feature flag or just per-route swap. Verify each page works.
  3. Delete Console's copies of comments.ts, discussion.ts, event-log.ts, sessions.ts, replies.ts, plan.ts, plan/block-html.ts, attachments.ts, ids.ts, lib/r2.ts. Compile errors point to anything that snuck a DB access in.
  4. Unify threads.ts — Worker's surface becomes the union of both. Console-only helpers (createThread, listThreads, approveThread, getConnectToken, deleteThread) move to Worker; Console calls them via HTTP.
  5. Console SSR auth — wire the Clerk JWT pass-through helper that signs Worker calls server-side. Standard Clerk pattern.

Each commit is independently revertable. The duplication is removed only in step 3, after the network path is proven in step 2.
