# Task 2.1 — DB schema + migrations (Slice 2)

## Problem

Slice 2 needs a durable wake-up queue (Mailbox), a per-Workspace hosted toggle,
and a VM run audit log. None exist yet. Slice 1d's presence registry is
in-memory only; it can't survive a Worker restart and it can't be polled by
a VM in another network. The Mailbox closes both gaps.

## The change

One Drizzle migration adds three things:

### 1. `mailbox_events`

| Column | Type | Notes |
|---|---|---|
| `id` | `text` PRIMARY KEY | `mbx_<random>` |
| `thread_id` | `text` NOT NULL | FK → `threads.id` |
| `event_id` | `text` NOT NULL | The event-log row that triggered this wake |
| `created_at` | `timestamptz` NOT NULL DEFAULT now() | |
| `consumed_at` | `timestamptz` NULL | Set when VM drains the row |

Constraints:

- Composite FK `(thread_id, event_id)` → `events(thread_id, id)` — events
  table is already PK'd on `(thread_id, id)`.
- `UNIQUE (thread_id, event_id)` — idempotent enqueue: duplicate writes for
  the same event are no-ops via `ON CONFLICT DO NOTHING`. Also satisfies the
  composite-FK uniqueness requirement.
- Partial index `(thread_id, created_at)` `WHERE consumed_at IS NULL` — the
  hot path is the drain query; this keeps the scan tight.

### 2. `workspaces.hosted_enabled`

`boolean NOT NULL DEFAULT false`. No index — read in the same query the
Worker already runs at enqueue time (Task 2.2 fetches the row).

### 3. `vm_runs`

| Column | Type | Notes |
|---|---|---|
| `id` | `text` PRIMARY KEY | `vmr_<random>` |
| `thread_id` | `text` NOT NULL | FK → `threads.id` |
| `started_at` | `timestamptz` NOT NULL DEFAULT now() | |
| `ended_at` | `timestamptz` NULL | |
| `exit_reason` | `text` NULL | Free-form; not an enum yet (small surface, easy to evolve) |
| `cost_estimate_usd` | `double precision` NULL | Filled at teardown |

Index on `(thread_id, started_at DESC)` for cost-roll-up queries.

## Deliberate simplifications (deletion test applied)

- **Dropped `kind` and `payload_json` from `mailbox_events`.** The plan doc
  lists them, but `event_id` already FK's to `events`, which holds both. The
  consumer reads at most a small batch; a JOIN to `events` is one query. If
  we duplicate the payload we own two copies of the same fact and the next
  schema migration that adds a `kind` has to touch two tables. *Skipped:
  denormalization; add when the JOIN shows up in a slow log.*
- **Dropped `scheduled_at` from `mailbox_events`.** "NULL = ASAP" with no
  caller is speculative. *Skipped: scheduled wakes; add when the first
  "recheck in 5 min" feature lands and we know the cadence.*
- **`exit_reason` is `text`, not an enum.** Two callers (teardown, supervisor
  crash) and a small known set. An enum requires its own migration to extend.
  *Skipped: enum; add when there are five+ values and they stop changing.*
- **No FK on `vm_runs.thread_id` cascade.** Threads aren't deleted in MVP.
  RESTRICT by default is fine.

## Alternatives considered

1. **`mailbox_events` keyed by `(thread_id, event_id)` as PK, no `id`
   column.** Cleaner — no synthetic id, the natural key carries weight. But
   every other Tempo table uses a `<prefix>_<random>` id for cross-table
   reference and log correlation; deviating here would surprise readers
   and complicate "find this mailbox row in the logs". Rejected.
2. **Put `kind` and `payload_json` back to avoid the JOIN.** Slice 2 plan
   suggests this. Rejected for the deletion-test reason above. The drain
   query is the only consumer and a 2-table SELECT under a partial index
   stays fast at expected scale (tens of pending rows per Worker boot).
3. **Skip `vm_runs` entirely; log to Pino.** Plan calls out cost-cap
   instrumentation that needs queryable history. Logs aren't queryable
   without infrastructure we don't have. Keep.

## Uncertainties

- **None blocking.** The MVP scale is small; if the partial index isn't the
  right shape we'll see it in pg_stat_statements before it matters.

## Layer assignment

- `packages/db/src/schema.ts` — table definitions (data layer).
- `packages/db/drizzle/0005_<name>.sql` — generated by `drizzle-kit generate`.
- `packages/db/src/ids.ts` — gains `newMailboxEventId()` and `newVmRunId()`
  helpers next to the existing `newEventId()`.

No app code changes in this task; Task 2.2 is the first writer.

## Deletion test (per added module/file)

- `mailbox_events` table — if removed, the entire Slice 2 wake-up path
  collapses. **Earns its keep.**
- `workspaces.hosted_enabled` — if removed, no way to gate Hosted per
  Workspace; Slice 2 acceptance check (#1) fails. **Earns its keep.**
- `vm_runs` table — if removed, no cost-cap path and no postmortem for VM
  exits. Slightly fuzzier; included because the Slice 2 plan explicitly
  calls out cost instrumentation as MVP requirement (out-of-scope §3).
  **Earns its keep, with the caveat that if cost-cap gets pushed to a
  later slice, this table goes with it.**

## Execution

```bash
bun run --filter @tempo/db db:generate    # writes drizzle/0005_*.sql
bun run --filter @tempo/db typecheck
bun run --filter @tempo/db lint
# Migration applies in dev via the existing migrate script.
```

## Acceptance

- `drizzle-kit generate` produces a clean migration with no schema diff
  after run.
- `bun run typecheck` clean across all packages.
- `bun run lint` clean on `packages/db`.
- Migration applies idempotently against a dev Postgres.

No code-reviewer or simplifier pass is needed for a schema-only change; the
plan is the artifact. Task 2.2 (the first writer) goes through the full
review pipeline.
